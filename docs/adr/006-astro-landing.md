# 006. Astro for Marketing Landing Pages

**Date**: 2026-10-19

**Status**: Accepted

**Deciders**: Igor Lukashenya

## Context

The monorepo needs to produce marketing landing pages that are translated into multiple
languages, optimized for search engines (SEO), and indexable by AI tools (Generative Engine
Optimization, or GEO). Landing pages are static, content-light sites with a fast time-to-value;
they don't need a client-side framework, a backend, or server rendering.

## Decision

Use **Astro** (static output) for marketing landing pages, generated by the `astro-landing`
stack (`make new-app STACK=astro-landing NAME=<name>`):

- **Framework**: Astro 7 (static output) with TypeScript and Tailwind CSS v4 (`@tailwindcss/vite`).
- **Translation**: Astro's built-in i18n routing (`defaultLocale: 'en'`, `locales: ['en', 'es']`,
  `prefixDefaultLocale: false` — `/` is English, `/es/` is Spanish), with per-locale typed
  dictionaries in `src/i18n/` and a language switcher.
- **SEO**: a `<Seo>` component emits title, description, canonical URL, `hreflang` alternates,
  Open Graph + Twitter cards, and JSON-LD; `@astrojs/sitemap` emits `sitemap-index.xml`
  (with hreflang alternates); `src/pages/robots.txt.ts` emits `robots.txt`.
- **GEO (per-language)**: `public/llms.txt` + `public/llms-full.txt` for every supported locale
  (`/llms.txt` and `/es/llms.txt`), linked from the page head via
  `rel="alternate" type="text/markdown"` and `rel="describedby"`, so AI tools
  (ChatGPT, Perplexity) can read and cite the site. **Adding a locale requires adding its GEO
  files** — this contract is documented in the template README and AGENTS.md.
- **Deployment**: static site served by nginx via Docker; tagged `deployable` like `react-web`.
- **Maintenance**: `sync-templates.sh` keeps the template's dependency versions in sync with the
  reference landing app `apps/landing` (which Dependabot keeps updated).

## Consequences

### Positive

- **Fast, static output**: no server runtime; nginx serves pre-rendered HTML, good for SEO and
  cheap to host.
- **Built-in SEO + GEO**: canonical/hreflang/sitemap/robots/llms.txt come with the scaffold, not
  as afterthoughts.
- **Low-friction i18n**: adding a language is a few files (config, dictionary, page, two GEO files).
- **Familiar monorepo contract**: same moon tasks, versioning, and `deployable` deployment as
  other stacks.

### Negative

- **Per-language GEO is a manual contract**: adding a locale requires also adding its `llms.txt`
  files; forgetting them leaves that language invisible to AI tools (mitigated by the documented
  four-step "adding a language" checklist).
- **Astro/Tailwind/ESLint drift**: fast-moving tooling; mitigated by `sync-templates.sh` +
  Dependabot on `apps/landing`.
- **`llms.txt` adoption is uneven**: it complements (not replaces) sitemap/robots/on-page SEO.

### Neutral

- `site_url` is overridable at build time via `SITE_URL`; the scaffold ships an `example.com`
  placeholder until a real domain is supplied.

## Alternatives Considered

### Option A: Next.js / React (SPA or SSR) for landing pages

- Pros: shared React skills across the repo, rich ecosystem.
- Cons: client-side JS for a content-only page; SSR needs a Node runtime; heavier than a static
  site for marketing pages.

### Option B: Hand-rolled static sites (no generator)

- Pros: no template to maintain.
- Cons: no consistency, no SEO/GEO/i18n defaults, manual per-site setup.

### Option C: A CMS-backed landing page

- Pros: non-developers can edit copy.
- Cons: operational overhead (database, auth, hosting); out of scope for a static marketing site.
